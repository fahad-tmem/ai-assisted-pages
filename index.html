Building AI Agents

An agent is a model plus a loop. The loop calls the model, runs the tools the model asks for, feeds the results back, and stops when the work is done or a limit is reached. Everything else is a set of decisions. You either make each one yourself or hand it to a product.

It is nine decisions, not one

Model, inference route, loop, orchestration, state, execution environment, tools, authority and evaluation. A product makes some of them for you.

Lock-in comes in parts

Swapping the model is usually cheap. Swapping the loop library or the host is expensive. Prompts tuned to one model never move for free.

Quality comes from the model and its inputs

Model fit, what the model sees each turn, tool design and deterministic checks matter most. The framework rarely does.

The harness still matters

The same model scores up to 8 points apart on Terminal-Bench 2.1 depending on the loop around it.

Authority lives outside the model

Code at the tool boundary decides what an agent may do. A prompt cannot enforce permissions.

Measure before you switch

Own what is your product's value, rent the rest, keep rented parts replaceable. Let a leak-free evaluation decide, and change one thing at a time.

Vocabulary

Terms

Most confusion about agents comes from one word meaning two things. These are the meanings used on this page.

Model
The LLM that reasons and chooses actions. Not the product that wraps it.
Inference route
Where and on what terms the model runs: the vendor's API, a cloud marketplace, self-hosted serving such as vLLM, or a gateway. The same model on two routes can differ in features, data terms and refusals.
Agent loop
The code that calls the model, runs the requested tools, appends the results and decides when to stop.
Harness (loop harness)
The loop plus what makes it work well: caching, compaction, paging of large tool output, built-in tools, recovery, budgets and subagents.
Harness text
The editable material the agent works from: system prompt, rules, skills, scripts and tool guidance. Some research calls this "the harness" too. This page keeps the two apart.
Thin agent SDK
A library that gives you the loop and leaves tools, sandbox, state and hosting to you. OpenAI Agents SDK, Google ADK, Pydantic AI.
Full harness as a library
A finished agent with built-in file, shell and web tools that you embed. Claude Agent SDK, Codex SDK, OpenHands SDK.
Orchestration framework
A library for structuring multi-step work as graphs or state machines, usually with checkpoints. LangGraph, Microsoft Agent Framework workflows, CrewAI flows.
Durable execution engine
Infrastructure that records progress so work survives crashes and restarts. Temporal, Restate, DBOS, Dapr.
Managed agent runtime
A vendor hosts the loop, the sandbox or both. Claude Managed Agents, Amazon Bedrock AgentCore, Microsoft Foundry Agent Service.
Execution environment
Where the side effects of tool calls happen: your process, a container, a gVisor or microVM sandbox, or a hosted sandbox.
Tool protocol
A standard interface: MCP connects tools and resources to models; A2A connects agents to agents.
Skill
A packaged procedure in the open Agent Skills format (SKILL.md plus references and scripts), loaded only when needed. It carries knowledge, never permission.
Evaluation fixture
A task with a known answer key, used to measure an agent. The key never reaches the agent, or anyone editing its instructions.
The stack

The nine decisions behind every agent

Every agent system answers these questions, either on purpose or by accepting a product's defaults. They group into four layers.

What thinksThe intelligence and where it runs
  • ModelWhich model is good enough at this specific task?Choosing from public leaderboards instead of your own evaluation.
  • Inference routeWhere can the model run, under whose data, retention and usage terms?Treating the route as a config value when its policy differs.
How it runsThe machinery around the model
  • Loop and harnessWho writes the call-tools-repeat loop and its context management?Underestimating what a mature harness already does.
  • OrchestrationHow is multi-step work structured, and who decides the structure?Letting a model invent structure where cost and consent must be known first.
  • State and durabilityWhat must survive a crash, and at what grain?Checkpointing the conversation and assuming the outside world comes back too.
  • Execution environmentWhere do side effects run, and how isolated?Running model-chosen commands without a sandbox.
What it may doCapabilities and limits
  • Tools and protocolsWhat can the agent do, through which interface?Too many tools, too coarse tools, or raw output dumped into context.
  • AuthorityWho decides what is allowed, and is it enforced outside the model?Trusting the prompt to enforce permissions.
How you knowProof and cost
  • Evaluation and observabilityHow do you know it works, and what it cost?No ground truth, only "the output looks good".
Bundles of decisions

Seven ways to build

Products and libraries bundle the nine decisions differently. Read the table as who decides each one by default. Real systems often combine two or three approaches.

The product or library decides Shared: it provides, you configure You build and decide
ApproachModelRouteLoopOrches­trationStateEnviron­mentToolsAuthorityEvaluation

These are typical defaults. Self-hosting, managed add-ons and configuration move the lines. Evaluation is yours in every approach.

1. Use a hosted agent product

ChatGPT agent features, Claude apps, Gemini Enterprise agents

FitsIndividual and team productivity.

Watch outNo product control. Data terms are the vendor's.

2. Extend an existing agent

Claude Code, Codex CLI, Gemini CLI, OpenCode, Goose. Embedded: Claude Agent SDK, Codex SDK, OpenHands SDK

FitsDeveloper automation, and products whose job matches the agent's built-in shape, which is mostly coding.

Watch outIts tool and permission model may not match yours. Some run one vendor's models only. Commercial terms apply.

3. Visual or low-code builder

n8n, Dify, Microsoft Copilot Studio

FitsBusiness processes owned by non-engineers, with many SaaS connectors.

Watch outWeak testing and versioning. Vendor builders can be short-lived: OpenAI's Agent Builder launched in October 2025 and closes on 30 November 2026.

4. Thin agent SDK

OpenAI Agents SDK, Google ADK, Pydantic AI, Microsoft Agent Framework

FitsProducts with their own tools, policies and platform.

Watch outYou build harness maturity yourself. Most are still 0.x and release weekly.

5. Orchestration framework

LangGraph, Microsoft Agent Framework workflows, ADK 2 graph workflows, CrewAI flows

FitsLong-running, branching workflows with human approvals, written by engineers.

Watch outWorkflows become code. It can duplicate an orchestrator you already have.

6. Managed agent runtime

Claude Managed Agents, Bedrock AgentCore, Google Agent Runtime, Foundry Agent Service

FitsTeams with no agent infrastructure who accept the vendor's cloud.

Watch outData residency and retention, cost, and lock-in at the hosting layer.

7. Own loop and platform

Direct model API calls inside your own system

FitsUnusual constraints, or when you already own most of the harness.

Watch outYou rebuild context management, recovery and tool plumbing that mature harnesses have already refined.

"SDK" names two different things

The OpenAI Agents SDK is a thin loop. The Claude Agent SDK is Claude Code packaged as a library, with built-in tools, and runs Claude models only. The line moves too: in 2026 the OpenAI SDK added sandbox agents with shell, filesystem, skills and compaction.

SDK versus framework is emphasis

Both are libraries that can run an agent loop. SDKs centre on the agent; frameworks centre on the workflow around it. Either can be model-agnostic.

Approaches combine

A common production shape owns orchestration, authority and state in its own platform, and rents only the loop inside each step from a thin SDK.

Portability

Lock-in comes in parts

"Can we switch?" has six separate answers. Check each one.

KindCheap whenExpensive when
ModelThe loop speaks a standard wire format such as OpenAI-compatible Chat CompletionsYou depend on model-specific features or a vendor's structured-output guarantee
Loop libraryIts imports live in one module and you own your data contractsIts types are everywhere, or you use its internal modules
Vendor-only featuresYou use only portable featuresFor example, the OpenAI Agents SDK rejects its Responses-only features on Chat Completions backends
HostingYou host itA managed runtime holds your sessions, memory and sandboxes
Data and tracesTranscripts and traces live in your databaseTraces go to the vendor by default. The OpenAI Agents SDK uploads them to OpenAI unless you turn it off
BehaviourYou have an evaluation that shows the gapPrompts and skills were tuned on one model. They always behave differently on another

Replacing a loop library costs more than its core. The call-tools-repeat core is a few hundred lines. Production parity also covers streaming tool-call assembly, request and history conversion, tool context and error responses, lifecycle hooks, turn limits that keep completed history, and cancellation. Ignoring a library's events does not mean you are not using its processing. List what your code actually consumes from it before estimating a swap.

Where results come from

What makes an agent good

Roughly in order of impact. Before switching frameworks, use an evaluation to find which of these is your bottleneck.

  1. Model fit for the task

    Measured on your tasks, not on generic leaderboards.

  2. What the model sees each turn

    Relevant evidence, a stable prompt prefix that can be cached, large output paged instead of dumped, text instead of encoded binary, old turns summarised or cleared.

  3. Tool design

    The right granularity, narrow reads, bounded outputs, and errors that tell the model what to do next.

  4. Deterministic verification

    The model decides what to try. Assertions, exit codes, parsers and schema checks establish what happened.

  5. Harness maturity

    Compaction, caching, retries, recovery and subagents. See the chart below.

  6. The orchestration framework

    It affects how reliably multi-step work runs. It rarely affects how well the agent reasons.

From a production audit agent

12.7M input tokens for 59K output, 8% cached

The run stopped before writing its report. A countdown in the system prompt broke caching on every turn, and source files arrived base64-encoded. That was an engineering defect in what the model saw, not a limit of the model.

The effect ranges from nothing to about 8 points and does not always favour the vendor's own harness. Source: Snorkel Terminal-Bench 2.1 leaderboard, read 20 October 2026.

Diagnose misses cheapest first

  1. Capability the agent lacks

    Tools, toolchains and access. No prompt or model fixes a missing tool.

  2. Harness text

    Instructions, skills and scripts. Cheap to change, but only on evidence.

  3. Sampling

    Do several independent attempts find more than one does?

  4. The model

    A model comparison under one loop measures models under that loop. It does not isolate the loop.

  5. The loop harness

    Last, because it is the most expensive to change.

One small measurement is a seed, not a verdict. Repeat runs and report the spread before you trust a difference.

Compute can buy recall. Several independent attempts, with their findings combined, can find more than one attempt. That only works where repeated runs have no side effects, and when findings have a stable identity so duplicates can be merged. Measure the combined result against a single run before you build it.

Autonomy

Declare the structure, free the tactics

How you build an agent and how much freedom it gets are separate choices. The pattern that suits most products is to let the platform fix the shape of the work and let the model choose how to do each part.

The platform declares

  • Which steps exist and how they depend on each other
  • What each step may touch
  • Budgets and time limits
  • Required outputs
  • What the user agreed to before launch

The model chooses

  • Which tools to use, and in what order
  • How deep to dig
  • When evidence justifies more work, within pre-approved templates
  • How to explain what it found

This keeps what users and operators need to know in advance: what they are authorising, what it will cost, and whether two runs can be compared. A planner agent that invents the structure gives up all three. Use one only where they do not matter.

Capturing model gains

As models improve, every tactic you encode outside the model becomes a ceiling. A thin loop passes improvements straight through. What matters is how much tactic you encode, not which framework you use: a graph framework with one free agent node passes gains through too.

The gains are almost free, not free. A new model needs conformance checks, re-tuned prompts, re-sized limits and measurement on your own tasks. Prompts written for a weaker model are often too prescriptive for a stronger one. Not all structure should loosen:

Invariants

Permissions, consent, runaway budgets, evidence records, output validation.

Keep them.

Policy and allocation

Turn and time budgets, task breadth, procedural checks.

Adjust per workflow, ideally as data rather than code.

Model-specific heuristics

Retry counts, prescriptive prompt wording, workarounds for a serving quirk.

Retune or retire per model, with measurement.

Published research points the same way. In the Harness² paper (2026), harness-text edits tuned for a weaker model added 17.3 points on one benchmark for another weak model, but only 2.6 for a frontier model.

Durable rules

Design principles

These hold whatever framework or vendor you choose.

Scope

  • Start simple. One call, then a fixed workflow, then an agent. Add agency only where the work cannot be specified in advance.
  • Use the fewest agents that work. Split only for different tools, models or permissions, or when one context would overflow.

Safety

  • Keep authority outside the model. Permissions, consent, budgets and approvals are enforced in code at the tool boundary.
  • Authorize effects, not commands. Constrain destination, effect class, budget and credentials, and leave the command vocabulary open.
  • Enforce at a boundary the agent cannot route around. An agent with its own shell can bypass tool-level permissions. Route its traffic through a policy proxy that adds credentials, classifies, budgets and records each request, and block direct egress. Keep what the program receives, what you retain as evidence, and what the model sees apart.
  • Treat everything the agent reads as untrusted. Web pages, repositories, tool output, documents and uploaded skills can all carry prompt injection.
  • Isolate execution in proportion to risk: container, gVisor or microVM.
  • Make side effects safe to repeat, and confirm destructive ones at the point of use.

Reliability

  • The model proposes; deterministic code confirms. A model's opinion of a screenshot is never the only evidence of a pass or fail.
  • Validate structured output. One self-hosted model returned malformed JSON in 3 of 4 samples with strict mode on.
  • Persist at task boundaries in your own data model. Restoring a conversation does not restore a browser session, a login or test data.

Context and cost

  • Bound every loop: turns, tokens, time, money and side effects. Reserve budget for the final report.
  • Engineer the context. Stable prefix, decoded text, paged output, narrow reads, only the schemas the step needs, old tool output cleared.

Change

  • Evaluate on real tasks with ground truth. Measure recall, precision, cost per completed task and variation across repeats. Re-run on every model or harness change. One improved case proves nothing.
  • Keep the answers away. Answer keys and grader output never reach the agent or anyone editing its instructions. Task prompts describe the work, not its measurement, and eval runs cannot fetch published answers.
  • Change harness text only on execution evidence. Cite the run behind each edit, change one thing at a time, and record each as helped, hurt, no effect or confounded. In published research, edits made without evidence lowered a benchmark score from 73.4 to 63.2.
  • Keep rented parts replaceable. Confine library imports, own your data contracts, and keep a conformance test per model and per loop.
  • Treat model and endpoint capabilities as dated measurements. Vendor APIs and self-hosted serving both change without notice.
Three recurring questions

Durability, multiple agents, and skills

Surviving crashes: pick the grain

Conversation

Saves message history and run state. Tools: SDK sessions, resumable run state. Fits chat-like products.

Step

Saves progress inside a workflow graph. Tools: LangGraph checkpoints, Temporal, Restate, DBOS, Dapr. Fits long, expensive steps that must not repeat.

Domain

Your own records of tasks, attempts and outputs; a crashed task restarts from its inputs. Fits products with clear task boundaries. Usually the right default.

Work that spans days or weeks, such as an engagement with human approvals, should be a durable business record containing bounded runs. Do not keep one agent loop alive for weeks.

More than one agent

Helps when
  • Sub-tasks are independent and can run in parallel
  • One context would overflow
  • Sub-tasks need different tools or permissions
  • A separate context should review the work
Costs
  • Tokens multiply
  • Coordination fails in new ways
  • Evaluation gets harder
Patterns
  • Coordinator with workers
  • Agents called as tools
  • Hand-offs between specialists
  • Declared fan-out: a template the evidence can instantiate several times

Skills and extensibility

Use the open format. Agent Skills (SKILL.md plus references and scripts) became an open standard in December 2025 and is supported by Codex and many other agents. A skill loads in stages: name and description first, the body when needed, references on demand.

A skill is knowledge, not authority. If a skill could declare its own permissions, any uploaded file could grant itself power. Permissions come from the platform.

Skills are less portable than they look. A skill assumes a tool shape, such as shell, file editing and web access, and was tuned on one model. Under a different harness or model it behaves differently. Measure parity before you promise it.

Scripts and skills carry more than prose. In published ablations, removing skills or scripts hurt more than removing prompt text. Prefer a deterministic script to a triggered procedure, and a triggered procedure to always-on prose.

Never learn from untrusted runs. A self-improvement loop that learns from customer or attacker-reachable runs can write injected text into skills that every later user receives. Learn only from fixtures you own, and ship changes through your normal reviewed release path.

Workflows as data scale better than workflows as code. If end users will extend your product, a declarative workflow document can be validated, signed, priced and shown to the user before it runs. A workflow written as framework code needs an engineer and a review for every change. A graph framework can still run behind a declarative format as an internal executor; what matters is what users author and what you can check before it runs.

Answer these first

  1. Which quality factor is your bottleneck, according to an evaluation?
  2. What must be enforced outside the model?
  3. Who will author workflows: engineers, administrators or end users?
  4. Where may data and models run?
  5. Does work outlive a process, and does it pause for humans?
  6. How much harness engineering can the team sustain?
Corrections

Common misconceptions

Each of these appears often in vendor material and in AI-generated advice.

HeardThe approaches form a ladder from easy to powerful.

In practiceThey are bundles of nine separate decisions. More control does not mean a better agent.

HeardAll agent SDKs are the same kind of thing.

In practiceSome are a thin loop and some are a full agent with built-in tools. The Claude Agent SDK also runs Claude models only.

HeardA better orchestration framework makes a smarter agent.

In practiceA framework makes multi-step work more reliable. Reasoning quality comes from the model, its context, its tools and the checks around it.

HeardSwitching models is a config change.

In practiceThe wire format may be. The behaviour is not. Prompts and skills tuned on one model change on another, so measure the difference.

HeardCheckpointing the agent lets you resume anything.

In practiceIt restores the conversation. The browser session, the login, the test data and every side effect stay as they are.

HeardStrict JSON mode guarantees valid output.

In practiceIt depends on the serving stack. Validate every response.

HeardThe prompt can define what the agent is allowed to do.

In practiceOnly code at the tool boundary can enforce it. A prompt can be argued with, including by text the agent reads.

HeardA smarter new model is a free upgrade.

In practiceAlmost free. It needs conformance checks, re-tuned prompts, re-sized limits and measurement on your own tasks.

HeardMore instructions can only help the agent.

In practiceEdits made without execution evidence have been measured making agents worse, and always-on prose is the most expensive place to put knowledge.

HeardThe framework list from last year still holds.

In practiceAutoGen went into maintenance mode in 2025 and Microsoft Agent Framework replaced it. OpenAI's Agent Builder closes 14 months after launch. Re-check before you choose.
